# Бот моніторингу оголошень OLX / eBay

Telegram-бот стежить за новими оголошеннями на OLX та eBay за фільтрами користувачів і надсилає сповіщення. Окремо є веб-адмінка: статистика, користувачі, дії адміна та заготовка під монетизацію.

## Архітектура

| Частина | Каталог | Запуск | Що робить |
|---|---|---|---|
| Бот (Telegraf) | `client/` | `npm start` | Спілкується з користувачами, доставляє сповіщення, повідомляє API про активність і результати доставки |
| API + poller | `server/` | `npm start` | REST для бота, опитування OLX/eBay, вебхуки платежів, щогодинне обслуговування |
| Адмін-панель | `server/admin/` | `npm run admin` | Окремий процес, за замовчуванням слухає лише `127.0.0.1:3100` |
| PostgreSQL | `docker-compose.yml` | `docker compose up -d` | Спільна база для API та адмінки |

Бот не звертається до БД напряму, тільки через API. Адмінка працює з тією ж БД, що й API.

## Швидкий старт

```bash
docker compose up -d                 # Postgres
cd server
cp .env.example .env                 # заповніть значення
npm install
npm run migrate                      # базові таблиці + міграції з server/migrations
npm start                            # API + poller

cd ../client
cp .env.example .env
npm install
npm start                            # бот
```

API накочує міграції й сам під час старту, тож `npm run migrate` потрібен насамперед для адмінки та для перевірки, що все застосувалось.

## Міграції

- Базові таблиці (`searches`, `notifications`, …), як і раніше, створює `init()` у `server/db.js`.
- Нові зміни схеми лежать у `server/migrations/NNN_назва.sql`. Застосовані міграції записуються в таблицю `schema_migrations`.
- Кожна міграція виконується в окремій транзакції. Одночасні запуски API, адмінки та `npm run migrate` серіалізуються через advisory lock.
- Міграції лише **додають** нове: таблиці, nullable-колонки, індекси, view. Існуючі дані не змінюються.
- Нова міграція — це новий файл із наступним номером. Застосовані файли не редагуйте.

| Міграція | Що додає |
|---|---|
| `001_admin_panel.sql` | `bot_users`, `user_activity_daily`, `notification_log`, `user_errors`, `admin_audit_log`, `admin_sessions`; колонки `searches.last_notified_at`, `notifications.log_id` |
| `002_billing.sql` | `plans` (+ тариф `free`), `subscriptions`, `payments`, view `current_subscriptions` |

Користувачі, які були до міграції, переносяться в `bot_users`. Їхня дата реєстрації береться наближено, за першим пошуком, снайпом або токеном eBay. Історії активності до встановлення трекінгу немає.

## Адмін-панель

### Створення адміна

Облікові дані адміна зберігаються в `server/.env`. У базі адмінів немає, у `.env` лежить тільки хеш пароля.

```bash
cd server
npm run admin:hash-password          # введіть пароль (від 12 символів), він не відображається
```

Скрипт виведе рядок `ADMIN_PANEL_PASSWORD_HASH='$2b$12$…'`. Вставте його в `.env` разом з одинарними лапками, а також:

```env
ADMIN_PANEL_USER=admin
ADMIN_PANEL_SESSION_SECRET=<32+ випадкових символів>
```

Секрет сесій можна згенерувати так:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Щоб змінити пароль, згенеруйте новий хеш і перезапустіть адмінку. Щоб примусово завершити всі сесії, змініть `ADMIN_PANEL_SESSION_SECRET` або очистіть таблицю `admin_sessions`.

### Запуск

```bash
cd server
npm run admin                        # http://127.0.0.1:3100
```

Якщо в конфігурації чогось не вистачає, адмінка не стартує і виводить список проблем. У продакшені її запускає pm2: див. застосунок `admin` в `server/ecosystem.config.cjs`.

### Розділи

- **Дашборд.** Користувачі (усього; нові за сьогодні, 7 і 30 днів; активні за 24 години, 7 і 30 днів), активні пошуки окремо для OLX і eBay, доставлені сповіщення за день і тиждень, скільки користувачів заблокували бота, графік нових і активних по днях. Блок монетизації: платні користувачі, дохід за місяць у розрізі валют, підписки, що закінчуються протягом 7 днів.
- **Користувачі.** Пошук за ID, @username та ім'ям. Фільтри за статусом, платформою, планом і періодом реєстрації. Сортування за будь-якою колонкою, серверна пагінація.
- **Сторінка користувача.** Дані, пошуки з датою останньої знахідки, останні 50 сповіщень зі статусом доставки, помилки, поточна підписка та її історія, платежі.
- **Дії адміна.**
  - Заблокувати або розблокувати користувача; при блокуванні причина обов'язкова.
  - Вимкнути, увімкнути або видалити пошук.
  - Видати або продовжити підписку вручну; причина обов'язкова. Скасувати підписку.
  - Редагувати тарифи на сторінці `/plans`.
- **Аудит** (`/audit`). Кожна дія адміна, а також входи, виходи й невдалі спроби входу: хто, що, коли, причина, деталі та IP. Запис робиться в тій самій транзакції, що й сама зміна.

Користувач, якого заблокував адмін, отримує від бота одне повідомлення «доступ обмежено», після чого бот його апдейти не обробляє. API не дає такому користувачу створювати пошуки, а poller не опитує його пошуки. Вимкнений адміном пошук користувач може знову увімкнути сам; щоб повністю закрити доступ, заблокуйте користувача.

### Безпека

- Пароль зберігається як bcrypt-хеш (cost 12). Логін і пароль перевіряються за однаковий час, незалежно від того, чи існує такий користувач.
- Сесії зберігаються в Postgres (`admin_sessions`). Cookie `admin.sid` має атрибути `HttpOnly` і `SameSite=Strict`, а `Secure` ставиться при HTTPS. Після входу видається новий id сесії. Тривалість сесії — 8 годин із продовженням при активності.
- CSRF: усі POST-форми містять synchronizer-токен із сесії. Форма входу захищена double-submit cookie.
- Невдалі входи обмежені: 10 спроб за 15 хвилин з одного IP (налаштовується).
- Заголовки ставить `helmet`: суворий CSP без inline-скриптів і стилів, `frame-ancestors 'none'`, `nosniff`, `no-referrer`. Відповіді мають `Cache-Control: no-store`.
- Без входу будь-яка сторінка редіректить на `/login`, а будь-який інший запит отримує 401. Невідомі шляхи поводяться так само.
- У логах лише метод, шлях, статус і час. Заголовки, cookie, тіла запитів і query string не логуються.
- Адмінка показує тільки потрібне для адміністрування. Токени eBay і сирі payload'и платіжних провайдерів не показуються.

### Вихід назовні через reverse proxy з HTTPS

Не відкривайте порт 3100 назовні. Адмінка має слухати `127.0.0.1`, а TLS бере на себе проксі на тому ж сервері. Приклад для nginx + Let's Encrypt:

```nginx
server {
    listen 443 ssl http2;
    server_name admin.example.com;

    ssl_certificate     /etc/letsencrypt/live/admin.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/admin.example.com/privkey.pem;

    add_header Strict-Transport-Security "max-age=31536000" always;

    # необов'язково: пускати лише з відомих IP
    # allow 203.0.113.10;
    # deny all;

    location / {
        proxy_pass http://127.0.0.1:3100;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

server {
    listen 80;
    server_name admin.example.com;
    return 301 https://$host$request_uri;
}
```

Сертифікат: `sudo certbot --nginx -d admin.example.com`.

У `server/.env` для продакшену:

```env
ADMIN_PANEL_HOST=127.0.0.1
ADMIN_PANEL_COOKIE_SECURE=true     # cookie тільки по HTTPS
ADMIN_PANEL_TRUST_PROXY=loopback   # довіряти X-Forwarded-* лише від локального проксі
```

`trust proxy` потрібен, щоб rate limit бачив реальний IP клієнта, а не IP проксі, і щоб cookie отримала прапорець `Secure`. Якщо проксі стоїть на іншій машині, вкажіть його адресу в `ADMIN_PANEL_TRUST_PROXY` і закрийте порт фаєрволом для всіх інших адрес.

## Трекінг активності

У боті (`client/script.js`) додано middleware, яке спрацьовує на кожен апдейт:

- **Реєстрація і активність.** Middleware викликає `POST /users/touch` у фоні, не частіше разу на 60 секунд для одного чату. Під час першої взаємодії API записує `created_at`. Під час кожної — оновлює `last_seen_at`, username, ім'я, мову та позначає поточний день як активний (`user_activity_daily`).
- **Швидкодія.** Відповідь бота не чекає на API. Виняток — перша взаємодія з чатом після рестарту бота: тоді він до 1,5 секунди чекає статус блокування. Помилки API логуються і на роботу бота не впливають.
- **Блокування бота користувачем.** Його фіксують два механізми:
  - подія Telegram `my_chat_member` (kicked / member);
  - помилка 403 під час доставки («bot was blocked by the user», «user is deactivated»).

  Пошуки такого користувача не опитуються, доки він знову не напише боту.
- **Доставка.** Кожне сповіщення надсилається окремо. Якщо доставка в одному чаті не вдалася, решта пачки все одно доставляється. Раніше одна помилка зупиняла всю пачку, а сповіщення з неї губились. Результати доставки бот надсилає в `POST /notifications/report`. Вони потрапляють у `notification_log` (історія), а помилки — у `user_errors`.

Історія сповіщень і помилок зберігається `HISTORY_RETENTION_DAYS` днів (за замовчуванням 90).

### Захист API бота (рекомендовано)

API на порту 3000 історично працює без авторизації. Якщо задати однаковий `BACKEND_API_TOKEN` у `server/.env` і `client/.env`, API вимагатиме заголовок `X-Api-Token`. Без цієї змінної все працює як раніше.

## Монетизація (заготовка)

Реальна оплата поки не підключена. Поки `PAYMENTS_ENABLED=false`, бот працює як раніше: діє ліміт `MAX_SEARCHES_PER_CHAT`, усі пошуки опитуються з інтервалом `POLL_INTERVAL_MS`.

- **Дані.** Таблиця `plans` містить ціну в мінімальних одиницях (integer), валюту, тривалість, ліміт пошуків, доступні платформи та інтервал перевірки. Таблиця `subscriptions` — статус, період, джерело. Таблиця `payments` — сума в мінімальних одиницях, провайдер, `external_id`, статус, сирий payload вебхука (jsonb). Даних карток у базі немає, тільки ідентифікатори провайдера.
- **Тариф `free`** позначений як тариф за замовчуванням. Його ліміти не менші за те, що вже є в користувачів. Хто не має активної підписки, автоматично отримує цей тариф.
- **Перевірка лімітів.** Усі ліміти перевіряються тільки через `server/billing/entitlements.js`: `getUserPlan`, `canCreateSearch`, `canUsePlatform`, `getCheckInterval`. Поточну підписку визначає view `current_subscriptions`.
- **Провайдери.**
  - `server/billing/providers/provider.js` описує інтерфейс `PaymentProvider` з методами `createInvoice()`, `verifyWebhook()` і `parseWebhook()`.
  - `mock.js` — заглушка для розробки й тестів, підпис HMAC-SHA256.
  - `index.js` — реєстр провайдерів.
- **Вебхук `POST /webhooks/payments/:provider`.**
  - Перевіряє підпис за сирим тілом запиту.
  - Блокує рядок платежу (`SELECT … FOR UPDATE`) і продовжує підписку тільки під час переходу в `paid`. Повторний вебхук з тим самим `external_id` нічого не змінює і отримує відповідь `200 {duplicate: true}`.
  - Якщо сума або валюта не збігаються з рахунком, платіж стає `failed`, а доступ не видається.
  - Повернення коштів (`refunded`) змінює лише статус платежу; підписку адмін за потреби скасовує вручну.
- **Створення рахунку.** `POST /billing/invoices` (`{chatId, planCode, provider}`) працює лише при `PAYMENTS_ENABLED=true`.

Локальна перевірка повного циклу з mock-провайдером:

```bash
# server/.env: MOCK_PAYMENT_SECRET=<будь-який рядок>, PAYMENTS_ENABLED=true; створіть платний тариф у /plans
curl -X POST localhost:3000/billing/invoices -H 'Content-Type: application/json' \
     -d '{"chatId":"123","planCode":"pro","provider":"mock"}'
npm run mock:webhook -- <external_id> paid <amount_minor> UAH
```

### Як додати реального провайдера

1. Створіть `server/billing/providers/<name>.js` з класом, що наслідує `PaymentProvider`:
   - `createInvoice` викликає API провайдера і повертає `{externalId, payUrl}`;
   - `verifyWebhook` перевіряє підпис провайдера за `rawBody`;
   - `parseWebhook` переводить статуси провайдера в `pending | paid | failed | refunded`.
2. Зареєструйте провайдера в `providers/index.js` під його ключами з `.env`.
3. У кабінеті провайдера вкажіть URL вебхука `https://<api-host>/webhooks/payments/<name>`.

Нотатки щодо конкретних провайдерів:
- **Telegram Stars**: валюта `XTR` без дробової частини, інвойс створює бот, а підтвердження приходить апдейтом `successful_payment`.
- **plata by mono, LiqPay, WayForPay**: сума в копійках, підпис вебхука перевіряється в `verifyWebhook`.

## Тести

```bash
cd server
npm test
```

Тестам потрібен `TEST_DATABASE_URL` (у `.env` або в змінних оточення). Кожен тестовий файл створює власну тимчасову схему, наприкінці видаляє її і таблиць у `public` не торкається.

Що покрито тестами:
- авторизація: вхід, невірний пароль або логін, CSRF, rate limit, вихід, атрибути cookie;
- доступ без логіну до всіх сторінок і дій;
- security-заголовки;
- запити статистики, фільтри, сортування й пагінація користувачів;
- entitlements з увімкненим і вимкненим прапорцем;
- вебхуки: підпис, ідемпотентність, зокрема одночасні дублікати, розбіжність суми;
- API трекінгу активності й доставки.
